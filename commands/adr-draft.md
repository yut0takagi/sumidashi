# /sumidashi:adr-draft

レビューで「衝突により保留」になった指摘や、同じ原則からの逸脱が繰り返される箇所について、チームの判断として記録するための ADR の下書きを作る。記録すれば、次のレビューからはその判断が ADR による例外として扱われる。

引数: `$ARGUMENTS`

## 手順

### 1. 材料を集める

- report.json のパスを渡されたら、それを読む
- 渡されなければ、`/sumidashi:review` の手順1〜5で report.json を作る（principle-reviewer の起動を含む）

report.json から次を拾う。

- status が held（衝突により保留）の指摘
- 同じチェックIDの指摘が、同じディレクトリかモジュールで3件以上あるもの
- 利用者が「意図的にそうしている」と言った指摘（会話にあれば）

材料がなければ「ADR にすべき判断は見つからなかった」と伝えて終わる。

### 2. 既存の ADR を確かめる

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/sumidashi" adr
```

同じ範囲・同じチェックを扱う Accepted の ADR があれば、新しく起こすのではなく、その ADR の scope・exempts を広げる案にする。番号の最大値を控える。

### 3. 下書きを作る

1つの判断につき1つの ADR。Michael Nygard 形式で書く。

```markdown
---
status: proposed
date: <今日の日付>
scope: [<対象のパスの glob>]
exempts: [<外れてよいチェックID>]
---
# <次の番号>. <判断を一文で>

## Status
Proposed

## Context
<どのチェックの指摘が、どこで何件出ているか。事実だけ>
<なぜその原則どおりにしていないのか（会話や既存コードから分かる範囲で。分からなければ「要記入」）>

## Decision
<利用者が決める。選択肢を2つまで並べ、空欄のまま渡す>

## Alternatives
<原則どおりに直す案と、そのコスト>

## Consequences
<この判断で得るもの>
<この判断で失うもの（外れる原則と、起きうる問題）>
```

- `scope` は対象のパスを最小の範囲で書く。広げすぎると、関係のない箇所の指摘まで消える
- `exempts` に正しさに関わるチェック（DDD-AGG-01・DDD-AGG-02・DDD-VO-01）を入れても、Info ではなく Low に留まることを Consequences に書く
- 書き上げた下書きが adr スキルの ADR-DOC 系に当たらないか、自分で確かめてから見せる

### 4. 確認して書き込む

下書きを見せ、Decision を利用者に埋めてもらう。承認されたら、設定の `adr.path`（既定は `docs/adr/`）に `<番号>-<短い英語の名前>.md` で書く。承認されるまで書き込まない。

## 守ること

- 決定の内容を利用者の代わりに決めない
- 外部への送信はしない
