# /sumidashi:plan

新機能の設計相談。要件を聞き、design-router が適用する思想を選び、レイヤー・境界・主要な型の案を出す。コードは書かない。

引数: `$ARGUMENTS`

## 手順

### 1. 要件を確かめる

引数だけで次が分からなければ、3問までに絞って聞く。分かっていることは聞かない。

- 誰が何のために使うか（アクターと目的）
- 守るべき業務ルール（条件、上限、状態による可否）
- 即時の一貫性が要る範囲（同じ操作の中で必ずそろっていなければならないもの）

### 2. 現状を調べる

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/sumidashi" layers
```

層マップ・規模・集約らしき型の推定を見る。関係しそうな既存のエンティティ・ユースケース・ADR（`docs/adr/`）・用語集（`docs/glossary.yml`）・業務ルール台帳（`docs/business-rules.yml`）があれば読む。

### 3. 適用する思想を決める

design-router スキルの適用判定（`skills/design-router/references/scale-matrix.md`）に従う。CRUD 中心や小規模なら、集約・リポジトリ・ドメインイベントを持ち込まない案にする。どの思想を当て、どれを当てないかを理由つきで1〜2文にする。

### 4. 判断を列挙して置き場所を決める

新機能に含まれる判断（業務ルール）を1つずつ書き出し、logic-placement スキルの判定手順（`skills/logic-placement/references/placement-procedure.md`）にかける。I/O を含むものは先に I/O と判断を分ける。

| 判断 | Q | 置き場所 | 理由 |
| --- | --- | --- | --- |
| クーポンが期限内か | Q1 | Coupon（値オブジェクト）の isValidAt(now) | 期限の値だけで決まる |
| 注文に適用できるか | Q3 | Order（集約ルート）の applyCoupon | 合計金額と明細という集約の不変条件に関わる |

### 5. 案を出す（2つまで）

案ごとに次を書く。

- 層ごとのファイルと主要な型（エンティティ・値オブジェクト・集約・ユースケース・ポート）。既存の層マップのディレクトリに合わせる
- 境界: どのポートを内側に定義し、どこが実装するか。境界を越えるデータの型
- トランザクションの範囲: 1トランザクションで変える集約。結果整合にするものはドメインイベントの名前（過去形）
- この案で当たらないようにしたチェック（例: CA-DEP-03、DDD-AGG-02）と、あえて受け入れるチェック（あれば ADR の起票を提案）
- トレードオフ: 変更するファイル数、テストのしやすさ、後から変えにくくなる点

案が2つあるときは、どちらを勧めるかを1つ決めて理由を書く。採らなかった案には「採らなかった理由」を1行で残す。

### 6. 次の一歩

勧める案で、最初に作るファイルとテストを3つまで挙げる。実装に進むかどうかは利用者が決める。利用者が承認するまでファイルを書かない。

## 守ること

- 案は2つまで。3つ目を足さない
- 規模に合わない重い設計を勧めない。ddd-tactical を適用しないと判定したプロジェクトでは、集約やリポジトリの導入を勧めない
- 既存の ADR の決定に反する案を出すときは、どの ADR に反するかを明記する
