# ロジック配置の判定手順

「このロジックはエンティティか、ドメインサービスか、アプリケーションサービスか」を、決まった手順で判定する。「サービス」という言葉はドメインサービスとアプリケーションサービスの両方に使われ、ここが曖昧なままだと、ロジックがサービスに集まって大きくなるため。

Q1 から順に確かめ、最初に「はい」になった場所に置く。内側に置けるものを外側に置かないための順番になっている。

## 前処理: I/O と判断を分ける

DB・API・現在時刻・乱数などの外部 I/O を含むロジックは、先に I/O と判断を分ける（CA-HUM-01）。判断の部分だけをこの手順にかける。I/O の部分は Q6（手順の調整）か、ポートの実装としてインフラ層に置く。

```text
取得（I/O）→ 判断（純粋）→ 保存・通知（I/O）
              ↑ ここだけを Q1〜Q5 にかける
```

## 手順

| Q | 問い | 「はい」なら置く場所 | 例 |
| --- | --- | --- | --- |
| Q1 | 判断が1つの値（またはいつも一緒に扱う値の組）だけで決まるか | 値オブジェクトのメソッド | 金額の加算、期間が重なるか、メールアドレスの形式 |
| Q2 | 判断が1つのエンティティの状態だけで決まるか | エンティティのメソッド | 注文をキャンセルできるか、会員ランクの昇格条件 |
| Q3 | 判断が集約の不変条件に関わるか（集約内の複数のエンティティにまたがるか） | 集約ルートのメソッド | 明細の合計数量の上限、確定後は明細を足せない |
| Q4 | 判断が複数の集約にまたがるか、またはどの1つのオブジェクトにも自然に属さないドメインの概念か | ドメインサービス | 口座間の振替、在庫の引き当て順の決定 |
| Q5 | このアプリケーション（ユースケース）に固有の規則か。業務全体のルールではなく、この画面・API・バッチの都合か | アプリケーションサービス（ユースケース）の判断 | 1回の API 呼び出しで扱う件数の上限、管理画面だけの絞り込み条件 |
| Q6 | 判断ではなく手順の調整か（リポジトリでの取得・保存、通知、トランザクション制御） | アプリケーションサービスの手順 | 注文を取得し、確定させ、保存し、確定イベントを発行する |

Q1〜Q6 のどれにも当たらないもの（外部システムとの形式の変換、プロトコルの都合）は、アダプタ層かインフラ層に置く。

## 指摘への書き方

指摘には、どの Q で結論が出たかを必ず添える（finding の `suggestion.placement`）。

- 「Q2 ではい。送料の判断は Order の状態だけで決まるので Order のメソッドに移す」
- 「Q1・Q2 はいいえ（2つの集約の状態が要る）。Q4 ではい。振替の可否は Account 2つにまたがるのでドメインサービスに置く」
- 「Q6 ではい。DomainService が repository.save と通知を行っているので、アプリケーションサービスに移す（PLC-02）」

## 既存チェックとの対応

配置の誤りのうち典型的なものは既存のチェックで拾う。新しい ID は作らず、この手順の結論を根拠として添える。

| 実際の置き場所 | 手順の結論 | 拾うチェック |
| --- | --- | --- |
| コントローラ・ハンドラ | Q2〜Q6 のどこか | CA-UC-01 |
| アプリケーションサービスやドメインサービス | Q2（単一のエンティティ） | DDD-SRV-01、DDD-ENT-02 |
| アプリケーションサービス | Q3（集約の不変条件） | DDD-AGG-02 |
| エンティティ・値オブジェクト | （I/O を含む） | PLC-01 |
| ドメインサービス | Q6（手順の調整） | PLC-02 |
| アプリケーションサービス | Q2〜Q4（業務判断） | PLC-03 |

## 迷いやすいところ

- 「現在時刻が要るから Q2 ではない」は誤り。時刻は I/O なので前処理で引数に変え、`order.canCancel(now)` として Q2 で判定する
- 「設定値（送料の閾値）が要るから Q2 ではない」も同じ。閾値を引数か値オブジェクト（ポリシー）として渡せば Q2 で決まる
- Q4 に落ちたら、本当に複数の集約が要るかをもう一度確かめる。1つの集約の中で閉じるなら Q3
- Q5 と Q2〜Q4 の見分け: 別の画面や API から同じ操作をしても守るべきなら業務全体のルール（Q2〜Q4）。その入口だけの都合なら Q5
