# logic-placement

ロジックの置き場所を決まった手順で判定し、置き場所の誤りと、横に増やせなくなる構造を見る。チェックの全文は [checks.yml](checks.yml)。

## スケールの2つの意味

- コードのスケール: 機能や人数が増えても、変更が1か所で済むこと。判断をできるだけ内側（データを持つ型）に置くほど、変更が局所化する
- 実行時のスケール: 負荷が増えても、サーバーを横に増やせば済むこと。サービスに状態を持たせないことと、即時の一貫性が要る範囲を小さく保つことが効く

## 配置の判定手順

Q1 から順に確かめ、最初に「はい」になった場所に置く。全文と例は [references/placement-procedure.md](references/placement-procedure.md)。

| Q | 問い | 置く場所 |
| --- | --- | --- |
| Q1 | 1つの値（値の組）だけで決まるか | 値オブジェクト |
| Q2 | 1つのエンティティの状態だけで決まるか | エンティティ |
| Q3 | 集約の不変条件に関わるか | 集約ルート |
| Q4 | 複数の集約にまたがるか、どの1つにも属さないドメインの概念か | ドメインサービス |
| Q5 | このユースケースに固有の規則か | アプリケーションサービスの判断 |
| Q6 | 判断ではなく手順の調整（取得・保存・通知・トランザクション）か | アプリケーションサービスの手順 |

判定の前に、外部 I/O を含むロジックは I/O と判断を分け（CA-HUM-01）、判断の部分だけをこの手順にかける。指摘にも `/sumidashi:plan` の配置提案にも、どの Q で結論が出たかを必ず添える。

## チェック一覧

| ID | 名前 | 判定方式 | 既定の重大度 | 収録 |
| --- | --- | --- | --- | --- |
| PLC-01 | エンティティが外部を呼ぶ | static | High | v1 |
| PLC-02 | ドメインサービスが手順を調整している | hybrid | Medium | v1 |
| PLC-03 | アプリケーションサービスに業務判断 | llm | Medium | v1 |
| SCL-01 | サービスが状態を持つ | hybrid | High | v1.5 |
| SCL-02 | 即時でなくてよい処理の同期化 | llm | Medium | v1.5 |
| SCL-03 | ドメインロジック起因の過剰な読み込み | hybrid | Medium | v1.5 |
| SCL-04 | 読み取りを集約経由で組む | llm | Low | v1.5 |
| SCL-05 | 更新が集中する集約 | llm | Medium | v1.5 |

v0.1 ではすべて draft。ddd-tactical を適用するときだけ走らせる（PLC-01 は層マップが推定できれば走る）。

## 既存チェックとの分担

配置の誤りのうち典型的なものは既存のチェックで拾い、新しい ID は作らない。手順の結論を根拠として添える。

| 実際の置き場所 | 手順の結論 | 拾うチェック |
| --- | --- | --- |
| コントローラ・ハンドラ | Q2〜Q6 のどこか | CA-UC-01 |
| アプリケーションサービスやドメインサービス | Q2 | DDD-SRV-01、DDD-ENT-02 |
| アプリケーションサービス | Q3 | DDD-AGG-02 |

## 判定するとき

- PLC-01: エンティティ・値オブジェクトがリポジトリや外部サービスを呼んでいる。解析器が確定する
- PLC-02: ドメインサービスがリポジトリでの取得・保存、通知、トランザクション制御を行っている（Q6 の仕事）
- PLC-03: アプリケーションサービスが、ドメインオブジェクトの状態で業務上の分岐・計算をしている（Q2〜Q4 の仕事）。Q5（このユースケースに固有の規則）なら指摘しない
- SCL-01: アプリケーションサービス・ドメインサービスが、リクエストをまたいで可変な状態（インスタンス変数、モジュール変数のキャッシュ）を持つ
- SCL-02: 業務上すぐに反映しなくてよい処理（通知、集計、他の集約の更新）が同じトランザクションに入っている。即時でなくてよいかはコードから決められない。業務ルール台帳に `consistency: immediate | eventual` があればそれに従い、なければ borderline に留める
- SCL-03: ループ内のリポジトリ呼び出し（N+1）、または判断に要らない集約全体の読み込み
- SCL-04: 一覧・集計など読み取り専用の画面を、集約を大量に読んで組み立てている（読み取りモデルを分ける候補）
- SCL-05: 多くのユースケースが同じ集約インスタンスを更新し、競合の焦点になる構造（グローバルなカウンタ、在庫の単一行など）

実行時の性能そのもの（応答時間、スループット）は測らない。見るのは、横に増やせなくなる構造だけ。

## 設計相談で使うとき

`/sumidashi:plan` では、新しい機能の判断を1つずつ列挙し、それぞれを Q1〜Q6 にかけて置き場所を決める。結果は「判断 → Q 番号 → 置き場所 → 理由1文」の表で示す。
