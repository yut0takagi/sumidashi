# model-commonality

共通化の見落としと、誤った共通化を両方向で見る。片方だけ見ると「何でも共通化しろ」と言うレビューになるため。チェックの全文は [checks.yml](checks.yml)。

## 共通化を勧める条件

次の3つをすべて満たすときだけ勧める。形が同じでも意味が違うもの（偶然の重複）は勧めない。

1. 同じ境界づけられたコンテキストの中にある
2. 用語集上で同じ概念を指す（用語集がなければ、両方の定義文を LLM が書き出し、一致するかを判定する）
3. 変更理由が同じ。同じ業務ルールの変更で、両方を直す必要がある

3つのうち1つでも決められないときは borderline にする。

## チェック一覧

| ID | 名前 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- |
| MDL-01 | 同一概念の重複定義 | hybrid | Medium |
| MDL-02 | 業務計算の重複実装 | hybrid | High |
| MDL-03 | 値オブジェクトにすべき組の散在 | hybrid | Medium |
| MDL-04 | 状態・区分の文字列散在 | static | Medium |
| MDL-05 | 誤った共通化 | llm | Medium |
| MDL-06 | 共有の型の再定義 | static | Low |

v0.1 ではすべて draft。ddd-tactical を適用するときだけ走らせる。business 台帳で generic に分類された領域では1段下げる。

## 判定するとき

- MDL-01: 同じコンテキストで、属性の集合が7割以上重なる型の組を解析器が候補に出す。上の3条件を満たすかを LLM が確かめる
- MDL-02: 同じ業務計算（税込金額、ポイント付与、手数料など）が2か所以上で別々に実装されている。候補はコードクローン検出（jscpd など）で出し、「同じ業務計算か」を LLM が確かめる。重複した業務計算は片方だけ直されて結果が食い違い、金額の不整合に直結するので High
- MDL-03: 金額と通貨、開始日と終了日など、いつも一緒に扱う値の組が、バラの引数で3か所以上に出る
- MDL-04: 状態や区分が文字列・数値リテラルのまま、3か所以上で比較されている
- MDL-05: 別コンテキスト、または別概念を1つの型にまとめた結果、片方の都合だけのフィールドや種別による分岐が増えている
- MDL-06: 共有カーネルとして定義済みの型があるのに、同じものを再定義している

## MDL-01 と MDL-05 がぶつかるとき

同じ型について「まとめよ」（MDL-01）と「分けよ」（MDL-05）が両方出ることがある。design-router の衝突ルールで裁定し、負けた側は「衝突により保留」として残す。どちらに転んでも、判断の根拠は上の3条件のどれが満たされないかで書く。

## 修正の示し方

- 共通化を勧めるときは、どちらの定義を残すか、残す型をどこに置くか（集約の内部か、共有カーネルか）まで書く
- 分割を勧めるときは、分けた後の2つの型の名前と、それぞれが持つフィールドを書く
- tradeoff には、変更するファイル数と、放置した場合にどんな食い違いが起きるかを具体的に書く
