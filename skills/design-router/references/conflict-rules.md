# 思想間の衝突と裁定ルール

同じ箇所に、複数のチェックが逆向きの修正を勧めることがある。たとえば「型を1つにまとめよ」（MDL-01）と「その共通化は誤りだ、分けよ」（MDL-05）。どちらかを黙って消すと、利用者は判断の材料を失う。そこで裁定の順番を固定し、負けた側も理由付きで残す。

## 裁定の順番

finalize がこの順で機械的にかける。LLM が出した指摘どうしの衝突で、design-router の `conflicts.yml` に書かれていないものも、同じ順で裁定する。

| 順 | ルール | 理由 |
| --- | --- | --- |
| 0 | ADR による例外を先に当てる | チームが記録して合意した判断を、一般論より優先する |
| 1 | 重大度 High の指摘を優先する | 正しさ（不変条件・データ整合）が壊れる指摘を後回しにしない |
| 2 | CA-DEP 系を、内部構造の指摘（DDD-AGG 系の分割など）より優先する | 依存の逆転は、後から直すほど高くつく |
| 3 | 変更ファイル数が少ない修正案を採る | 同じ価値なら、小さい変更のほうが入れやすい |
| 4 | 採らなかった側は消さずに「衝突により保留」として残す | 判断の材料を利用者から奪わない |

ルール0の例外: 正しさに関わるチェック（DDD-AGG-01・DDD-AGG-02・DDD-VO-01）は、ADR の exempts に入っていても Info ではなく Low に留め、毎回表示する。データ整合の問題を記録だけで黙らせないため。

## 衝突とみなす条件

次の3つをすべて満たすときだけ衝突として扱う。

1. 2つの指摘の location が同じファイルで、行範囲が重なる（または同じ型・同じ関数を指す）
2. 修正方針が逆向き（足す／削る、まとめる／分ける、層を増やす／増やさない）
3. design-router の `conflicts.yml` に組として書かれている、またはルーターが内容を読んで逆向きと判断した

同じ問題を別の言葉で言っているだけのもの（重複）は衝突ではない。checks.yml の `also_accept` で主と従を決め、従の側を「重複として統合」にする。たとえば GLO-04 と DDD-AGG-04 は同じ箇所を指すことがあり、DDD-AGG-04 を主にする。

## 規模判定との衝突

チェックどうしではなく、チェックと規模判定がぶつかることがある。

| 衝突 | 裁定 |
| --- | --- |
| CA-BND-01（変換層を足せ）と、小規模判定による「層を増やすな」 | 規模判定を優先し、CA-BND-01 を Info に下げる |
| DDD-VO-03（値オブジェクトを足せ）と、CRUD 中心の判定 | CRUD 中心なら ddd-tactical 自体を走らせないので、衝突は起きない |
| DDD-AGG-03（結果整合に分けよ）と、業務ルール台帳の `consistency: immediate` | 台帳を優先し、DDD-AGG-03 を出さない。台帳に記載がなければ borderline に留める |

## 保留の書き方

保留にした指摘は、report の「衝突により保留」欄に出す。次の3つを必ず書く。

- 勝った側のチェックIDと、どのルール（0〜3）で決まったか
- 負けた側の指摘の要約
- 負けた側の修正を採ったら何を得て何を失うか（1文）

同じ組み合わせの保留が繰り返し出るなら、`/sumidashi:adr-draft` で ADR の起票を勧める。チームとしての判断を記録すれば、次からはルール0で決まる。

## 未決のこと

裁定の順番を固定にするか、プロジェクトの設定で変えられるようにするかは、まだ決めていない（要件定義の未決事項）。v0.1 では固定にしている。
