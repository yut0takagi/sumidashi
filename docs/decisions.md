# 実装で決めたこと

要件定義に書かれていない点と、未決のまま残っている点を、実装でどう決めたかの記録。
決め直すときは、この文書を先に直してから実装と fixtures を合わせる。

## 要件定義の未決事項

| 未決事項 | いまの扱い | 理由・戻し方 |
| --- | --- | --- |
| 一次対応言語 | TypeScript と Python | 要件の案のまま。言語を足すときは `parse_<言語>.py` と `resolve.py` の解決規則を足し、fixtures を言語ごとに用意する |
| 衝突の優先順位を設定で変えられるか | 固定（R0-ADR → R0-SCALE → R1-HIGH → R2-DEPENDENCY → R3-FEWER-FILES、負けた側は R4-HOLD で held） | 設定で変えられると、同じコードでもリポジトリごとに結論が変わり、評価の正解データが作れない。変えたい箇所は ADR の例外で個別に外す |
| OSS のスキルを fork するか | ゼロから書いた。外部のスキルのコードや文章は取り込んでいない | fork しないのでライセンスの確認は要らない。書籍などの原典は checks.yml の sources で ID と書名を挙げるだけで、本文は引用しない |
| 社内配布か OSS 公開か | 決めていない。plugin.json に license を書いていない | 社内の仕組みに依存するコードは入れていないので、どちらにも進める。公開するなら license を決めて plugin.json と README に書く |
| 採点を出すか | 既定で出す。`.claude/sumidashi.yml` の `report.scores: false` で消せる | 点数が独り歩きしないよう、report.md では指摘一覧の後ろに置く。走らせたチェックがない思想には点を付けない |

## 重大度の調整

- 順番は「チェック固有の escalate・deescalate → 適用判定の1段下げ → ADR → 変更頻度・カバレッジ」。要件定義は、共通の調整を固有ルールより後に掛けると定めている。適用判定の1段下げも相対の調整なので、固有ルールで決まった重大度に後から掛ける
- 変更頻度は、直近90日に2回以上変更されたファイルの中で上位10%に入るものを1段上げる。2回以上という条件は、小さなリポジトリで1回変更しただけのファイルが上位に入るのを避けるため
- カバレッジは lcov と Cobertura を読む。設定の `coverage_path` がなければ、よく使われる置き場所を順に探す。見つからなければ、この調整は掛けない
- ADR で例外にした指摘には、変更頻度・カバレッジの引き上げを掛けない
- DDD-ENT-03 の escalate（集約ルートのフィールドが不変条件の検証に使われていれば High）は、v0.1 では実装していない。不変条件の検証に使われているかは、メソッドの本体でそのフィールドがどの条件式に出るかを追う必要がある。v0.5 で hybrid の候補として LLM に確かめさせる
- R0-SCALE の「小規模判定のとき CA-BND-01 を Info に下げる」も v0.1 では掛からない。CA-BND-01 がまだ draft で走らないため

## ロードマップからの前倒しと先送り

- ADR の読み込みと例外は、ロードマップでは v0.5 だが v0.1 で入れた。static のチェックしかない段階でも、意図して残している違反を毎回出すとノイズになり、評価基盤を試す人が離れるため
- hybrid の候補抽出は v0.5 に送った。v0.1 の facts.json の candidates は空で、hybrid のチェックはすべて draft のまま走らない。finalize は、候補にない箇所への hybrid の指摘を捨てる（要件定義「判定の仕組み」）

## 設定

- `layers` の glob が複数当たったら、最初のワイルドカードより前の部分が最も長い glob を採る。`src/**` と `src/domain/**` が両方当たれば後者
- `hooks.pre_pr_check` は既定で off。PR を作るたびに解析が走るので、使う人が明示的に有効にする
- `onboarding_until` の日付までは、適合率 0.9 以上のチェックだけを走らせ、strict を standard に読み替える

## 重複と衝突

- also_accept は「同じ問題を別の言葉で言う組」として扱う。A の also_accept に B があり、A と B の指摘の場所が重なったら、A を B にまとめる（B を残し、A は merged）
- 衝突の組は design-router/conflicts.yml に書いたものだけ。チェックの conflicts_with は、索引を作るとき（`catalog.build_index`）に conflicts.yml の組から両向きに補う
- SHACL は、ready のチェックに violation・borderline・not_violation の評価ケースがそろっていることを確かめる。draft のチェックは対象外

## 判定規則の細部

static-checks.md に書いた規則のうち、決めるときに迷ったもの。

- DDD-VO-02 の `set` アクセサ・Python の setter は、アクセサ1つで1件にする。中の代入まで数えると、同じ問題が2件に見えるため
- DDD-VO-02 の「readonly だが中身を変更できるコレクション」は、公開のフィールドだけを borderline にする。private のものは外から触れない
- attrs の `@define`・`@mutable`・`@attr.s` は dataclass と同じに扱う。`@frozen` と `frozen=True` は変更できないとみなす
- Pydantic の BaseModel を継承したクラスは、v0.1 ではエンティティ・値オブジェクトの可変性の指摘を出さない。フィールドを `__init__` で代入せずクラス本体で宣言するので DDD-ENT-03 の Python の規則に当たらず、dataclass でも ValueObject の継承でもないので値オブジェクトとも判定しない。変更できるかどうかは `model_config` の設定や基底クラスで決まり、静的には確定しにくい。誤検知を避けるほうを選んだ
- CA-DEP-02 の台帳は、`django` そのものではなく `django.http`・`django.db` などのサブモジュールで分類する。`django.utils` や `django.core.exceptions` まで web にすると、ドメイン層で例外の型を使っただけで違反になるため

## 評価

- 各ケースは、そのケースのチェックIDだけを走らせて採点する
- 突き合わせは、ファイルが同じで行範囲が重なれば一致とし、期待1件に指摘1件まで
- 適用判定のケースは、出荷ゲートを無視してすべての ready のチェックを走らせる。ゲートの結果で指摘の数が変わると、適用判定そのものの正しさを測れないため
- v0.1 の評価結果（すべて 1.00）は、fixtures と解析器を同じ判定規則から作ったので、規則どおりに実装できているかを示すだけで、実際のリポジトリでの精度は示さない。実際のコードでの精度は、ロードマップの v0.5 にあるセットBの注釈で測る
