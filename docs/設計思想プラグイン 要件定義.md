# sumidashi 要件定義

Oct 15, 2026 · @Ytkg

## 背景と目的

DDD・クリーンアーキテクチャ・SOLID・Kent Beck流の単純設計などの設計思想を1つのClaude Codeプラグインに束ね、設計段階のガイドとコードレビューの両方で使えるようにする。

既存のコミュニティ製スキルは思想ごとにバラバラで、粒度・出力形式・採点基準が揃っていない。思想同士が衝突する場面(例:YAGNI vs. 将来の拡張に備えた境界設計)の裁定もない。

目的は次の3つ。

- 設計思想を「原則・チェック項目・違反例・修正例」の同じ型で記述し、横断的に参照できるようにする
- 指摘を重大度とエビデンス(ファイル・行)付きで出し、レビュー結果を比較・追跡できるようにする
- プロジェクト規模と複雑さに応じて適用する思想と厳しさを切り替え、小さいコードに過剰設計を強いない

## スコープと前提

**対象**

- 形態:Claude Codeプラグイン(skills + agents + commands + hooks を同梱、marketplace経由でインストール)
- 利用場面:新機能の設計相談、PR・差分レビュー、既存モジュールのリファクタ方針づくり
- 言語:TypeScript と Python を一次対応。原則の記述は言語非依存にし、言語別の例を references に置く

**対象外**

- 自動リファクタの一括適用(提案と差分案まで。適用は人が判断)
- 性能最適化・セキュリティ監査(別プラグインの領分)
- ドメインエキスパートとのモデリングワークショップの代替

**前提**

- 利用者はClaude Codeを日常的に使うエンジニア。設計思想の名前は知っているが細部は曖昧、という層を主ターゲットにする
- 指摘の根拠は必ずコード上のエビデンスに紐づける。一般論だけの指摘は出さない

## 収録する設計思想とスキル構成

v1はクリーンアーキテクチャとDDD戦術設計の2思想に絞り、チェック項目を合計27個まで詰める。加えてADR系の9チェック、ドメイン用語の6チェック、モデル共通化の6チェック、ビジネス視点のうち2チェック、ロジック配置の3チェックを持ち、プロジェクト固有の判断と言葉を扱う。契約・規約はv1.5、形式手法とOWLはv2。全チェックは設計知識のオントロジー上で管理する。SOLID・単純設計・DDD戦略設計は、評価の土台ができてから足す。

絞る理由は3つ。

- 2思想とも、違反の多くが依存関係と型の構造に出る。静的解析で事実を取れるので、正解データを作りやすく評価がぶれにくい
- 2思想は「ドメインを外側の都合から守る」という目的が重なり、同じ層マップを共有できる
- SOLIDやコードスメルは判定者による揺れが大きい。評価の仕組みが固まる前に入れると、精度の議論が成り立たない

## 判定の仕組み

事実で決まるものは静的解析で確定し、LLMには解釈が要る判定だけを任せる。LLMに全部を任せると、同じ入力でも結果が揺れて評価が成り立たないため。

&#91;embedded content: レビューの判定パイプライン · 5段階\]

hybrid のチェックは、静的解析の候補にない箇所をLLMが新たに指摘することを禁じる。候補の網羅と確定の精度を別々に測れるようにするため。

## チェック項目の仕様

1チェック=1エントリで `checks.yml` に書き、判定基準・除外条件・評価用fixturesまで1か所で持つ。チェックの定義そのものが評価の単位になる。

| フィールド | 必須 | 中身 |
| --- | --- | --- |
| id | ○ | `<思想>-<区分>-<連番>`。一度振ったら変えない |
| name | ○ | 一行の名前 |
| principle | ○ | 守るべき原則を1文で |
| source | ○ | 原典の書名と章 |
| applies\_when | ○ | 適用する前提。層マップ上の層、言語、ファイル種別 |
| detection.type | ○ | `static`(静的で確定)/ `hybrid`(静的で候補、LLMで確定)/ `llm`(LLMのみ) |
| detection.static | static・hybrid | 依存ルール、tree-sitter クエリ、メトリクス閾値 |
| detection.question | hybrid・llm | LLMに投げる判定質問。YES/NOで答えられる形にする |
| criteria.violation | ○ | 違反とみなす条件。観察できる事実で書く |
| criteria.borderline | ○ | グレーとみなす条件。指摘は「要確認」に回す |
| criteria.not\_violation | ○ | 似ているが違反ではないケース |
| exclusions | ○ | 誤検知を防ぐ除外条件(テストコード、DTO、ファクトリ内など) |
| severity.default | ○ | 既定の重大度 |
| severity.escalate / deescalate | 任意 | 重大度を上下させる条件 |
| fix\_patterns | ○ | 修正パターン。差分案のひな形 |
| related | 任意 | 関連・競合するチェックID |
| fixtures | ○ | 違反・グレー・非違反の各サンプルへのパス |

記述例(DDD-AGG-01):

```yaml
- id: DDD-AGG-01
  name: 集約の外から内部エンティティを直接変更している
  principle: 集約内部の状態は集約ルートのメソッド経由でのみ変更する
  source: Evans『Domain-Driven Design』6章 Aggregates
  applies_when:
    layers: [domain, application]
    requires: aggregate_map   # 集約ルートと内部エンティティの対応が推定できること
  detection:
    type: hybrid
    static: >
      集約外のファイルから、内部エンティティの setter 呼び出し・
      フィールド代入・コレクションへの push/remove を列挙
    question: >
      この変更は集約ルートを経由せずに内部エンティティの状態を変えているか。
      ルートの不変条件チェックを迂回しているか。
  criteria:
    violation: 集約外のコードが内部エンティティの状態を書き換え、ルートのメソッドを通らない
    borderline: ルートが内部エンティティの参照を返し、呼び出し側が読み取りのみ行っている
    not_violation: ルートの中、または集約内のエンティティ同士での変更
  exclusions:
    - テストコード(tests/, *.spec.*, *_test.py)
    - 集約を組み立てるファクトリ・再構築用のリポジトリ実装
  severity:
    default: High
    deescalate: 対象の内部エンティティに不変条件が1つも定義されていない場合は Medium
  fix_patterns:
    - 変更操作を集約ルートのメソッドに移し、内部コレクションは読み取り専用で公開する
  related: [DDD-AGG-02, DDD-ENT-01]
  fixtures:
    violation: [evals/fixtures/ddd-agg-01/v1.ts, v2.py, v3.ts]
    borderline: [b1.ts, b2.py]
    not_violation: [n1.ts, n2.py]
```

新しいチェックは、fixtures が揃い、評価で出荷ゲートを通るまで既定で無効にする。

## 判定と重大度の定義

判定は3値、重大度は4段階に固定し、どちらも「観察できる事実」で決める。書き手の印象で上下させない。

**判定(verdict)**

| 判定 | 意味 | 出力の扱い |
| --- | --- | --- |
| violation | criteria.violation を満たし、exclusions に当たらない | 指摘一覧に出す |
| borderline | criteria.borderline を満たす、または判定に必要な情報がコード外にある | 「要確認」欄に出す。評価では誤検知にも見逃しにも数えない |
| not\_violation | どちらにも当たらない | 出さない。内部ログにだけ残す |

**重大度(severity)**

| 重大度 | 基準 | 例 |
| --- | --- | --- |
| High | 放置すると正しさが壊れる(不変条件・データ整合)、または依存方向が逆転して変更の波及が止まらない | 集約外からの直接変更、ドメイン層からORMへの依存 |
| Medium | 今は正しく動くが、変更コストかテストの難しさを確実に上げる | 1トランザクションで複数集約を更新、可変な値オブジェクト |
| Low | 局所的な改善余地。直さなくても波及しない | プリミティブ執着、イベント名が過去形でない |
| Info | 設計判断の記録として残すだけ | 意図的に層を飛ばしている箇所 |

**重大度の調整ルール**(全チェック共通。チェック固有の escalate / deescalate より後に適用)

- 該当ファイルの直近90日の変更回数がリポジトリ内で上位10%なら、1段上げる。変更が多い所ほど設計の歪みが効くため
- 該当箇所がテストで一度も実行されていなければ、1段上げる(Highは据え置き)
- 同じチェックIDの指摘が5件を超えたら、6件目以降は個別に出さず「同種の違反がN件」とまとめる
- 設定が `lenient` なら Low と Info を出さない。`strict` なら borderline も指摘一覧に出す

## 適用判定と思想間の衝突ルール

ルーターは「そもそも適用するか」を先に決め、適用しない思想のチェックは走らせない。過剰設計の勧めを、出力の段階ではなく入口で止めるため。

**適用判定(規模・複雑さ)**

| 条件 | clean-architecture | ddd-tactical |
| --- | --- | --- |
| 層マップが推定できない(全部1ディレクトリ等) | CA-DEP系のみ、重大度を1段下げる | 適用しない |
| ドメインロジックがほぼない(CRUD中心。判定はルーターのLLM判定+ドメイン層の行数比) | CA-DEP系のみ | 適用しない |
| 集約らしき型(ルート+所有する子)が推定できない | 通常どおり | AGG・REP系を外し、ENT・VO系のみ |
| 設定ファイルで明示 | 設定に従う | 設定に従う |

**衝突ルール**:同じ箇所に複数のチェックが逆向きの修正を勧めたとき、次の順で裁定する。

1. 正しさに関わる指摘(重大度High)を優先する
2. 依存方向に関わる指摘(CA-DEP系)を、内部構造の指摘(DDD-AGG系の分割など)より優先する。依存の逆転は後から直すほど高くつくため
3. それでも決まらなければ、変更ファイル数が少ない修正案を採る
4. 採らなかった側の指摘は消さず、「衝突により保留」として理由付きで残す

v1で想定している衝突の例:CA-BND-01(境界でORMモデルを使うな、変換層を足せ)と、小規模判定による「層を増やすな」。この場合は規模判定を優先し、CA-BND-01 を Info に下げる。

## ADRの扱い

ADR(Architecture Decision Record)を、設計思想と並ぶ「プロジェクト固有の判断基準」として扱う。一般論の設計思想より、そのチームが記録して合意した判断を優先する。

ADRに対してやることは4つ。

| 機能 | 内容 | コマンド |
| --- | --- | --- |
| ① ADRによる例外 | Accepted のADRで意図的に原則から外れると記録された箇所は、指摘を Info に下げ、根拠のADR番号を添える | `/sumidashi:review` に内蔵 |
| ② コードとADRの整合チェック | Accepted のADRの決定内容に反するコードを指摘する | `/sumidashi:review` に内蔵 |
| ③ ADR自体のレビュー | 新規・更新されたADRの書き方と中身を、型と設計思想の両面から見る | `/sumidashi:adr-review <パス>` |
| ④ ADR起票の提案 | 衝突裁定で保留にした指摘や、同じ例外が繰り返される箇所について、ADRの下書きを出す | `/sumidashi:adr-draft` |

**ADRの読み込み**

- 置き場所は既定で `docs/adr/`。`.claude/sumidashi.yml` の `adr.path` で変更できる
- 形式は Michael Nygard 形式と MADR を読める。どちらでもない場合は見出しから Status・Context・Decision・Consequences を推定し、推定できないADRは「形式不明」として①②の対象外にする
- 使うのは Status が Accepted のものだけ。Superseded は置き換え先を辿り、Proposed・Deprecated は参照しない
- ①②に使うため、ADRごとに機械が読める適用範囲を持たせる。ADRのフロントマターに `scope`(対象のパスやモジュール)と `exempts`(外れてよいチェックID)を書く。書かれていないADRは②の対象にするが、①の例外には使わない(範囲が曖昧なまま指摘を消さないため)

```yaml
---
status: accepted
date: 2026-09-12
scope: [src/reporting/**]
exempts: [CA-BND-01, DDD-ENT-02]
---
# 0007. 集計系はORMモデルを境界越えで直接使う
```

**ADRチェック項目**(カタログに ADR- 系として追加)

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| ADR-CMP-01 | 決定に反するコード | Accepted ADRの scope 内で、Decision に書かれた方針と逆の実装がある | llm | High |
| ADR-CMP-02 | 古いADRに従っている | Superseded のADRの決定に沿った実装が、新しく追加されている | hybrid | Medium |
| ADR-CMP-03 | 例外の範囲外への拡大 | exempts の対象チェックが、scope の外で同じ理由で破られている | static | Medium |
| ADR-DOC-01 | 必須項目の欠落 | Status・Context・Decision・Consequences のいずれかがない、または1文未満 | static | Medium |
| ADR-DOC-02 | 代替案がない | 検討した代替案と、採らなかった理由が書かれていない | llm | Medium |
| ADR-DOC-03 | 帰結が一面的 | Consequences に良い面しか書かれていない | llm | Low |
| ADR-DOC-04 | 原則からの逸脱が明示されていない | 決定内容が v1 のチェックに当たるのに、どの原則から外れるかと理由が書かれていない | llm | Medium |
| ADR-DOC-05 | 適用範囲が書かれていない | `scope` がなく、本文からも対象が特定できない | hybrid | Low |
| ADR-DOC-06 | 既存ADRとの矛盾 | Accepted の別ADRと決定内容が矛盾し、Supersedes の記載もない | llm | High |

ADR-DOC 系は書き方の指摘であって、決定の良し悪しは判定しない。決定そのものへの意見は、v1チェックに当たる場合にだけ、該当チェックIDと一緒に「この判断で失うもの」として添える。

**衝突ルールへの追加**:ADRによる例外は、衝突ルールの1(重大度High優先)より前に適用する。ただし正しさに関わるチェック(DDD-AGG-01・02、DDD-VO-01)は、ADRで exempts に入っていても Info ではなく Low に留め、毎回表示する。データ整合の問題を記録だけで黙らせないため。

## 設計知識のオントロジー

原則・チェック・ADR・評価データの関係を、1つの知識グラフとして持つ。ルーターの適用判定、衝突裁定、解説モード、評価の網羅チェックが、すべてこのグラフの問い合わせになる。

&#91;embedded content: 設計知識オントロジーのクラスと関係\]

**持ち方**:人が書くのは引き続き `checks.yml`、ADR、`glossary.yml`。ビルド時にこれらを RDF(Turtle)に変換し、プラグインが実行時に読む JSON の索引も生成する。実行時に推論器やSPARQLは使わない。レビューの速度と環境依存を増やさないため。

**整合性の検証**:グラフに SHACL の形状制約を掛け、CI で毎回検証する。合わなければビルドを落とす。

- すべての Check が1つ以上の Principle を守らせ、Principle は1つ以上の Source を持つ
- すべての Check に、違反・グレー・非違反の Fixture が各最低1つある
- conflictsWith は対称で、両端のどちらかに裁定ルールが付いている
- ADR が exempts で指す Check が存在し、scope が空でない
- also\_accept で結ぶ Check 同士が related でもつながっている

**このグラフでできるようになること**

- 評価の網羅レポート:チェックが1つもない原則、fixtures が足りないチェックを一覧にする
- 解説モードの深掘り:「この指摘 → 守らせる原則 → 出典 → このリポジトリで例外にしたADR」をたどって示す
- 思想の追加時の影響確認:新しいチェックが既存のどのチェックと競合しうるかを、同じ層・同じ原則を共有するものから候補に出す

## ドメイン用語オントロジー

ユビキタス言語を、概念と関係を持つ機械可読な用語集として持ち、コードの命名と型の関係に照合する。用語集が「読むだけのWikiページ」で終わり、コードとずれていくのを防ぐため。

**形式**:人が書くのは `docs/glossary.yml`。プラグインがこれを SKOS(用語・同義語・上位下位)と OWL の最小限の語彙(部分・全体、関連)に変換して使う。最初からTurtleを書かせると誰も更新しなくなるため、書く形式と使う形式を分ける。

```yaml
context: order          # 境界づけられたコンテキスト
terms:
  - term: 注文
    code_names: [Order]
    definition: 顧客が確定した購入の単位。確定後は明細を追加できない
    synonyms_deprecated: [オーダー, Purchase]
    relations:
      has_part: [注文明細]     # 集約の内部
      refers_to: [顧客]        # ID参照
  - term: 注文明細
    code_names: [OrderLine]
    definition: 注文に含まれる商品と数量の組
```

**チェック項目**(GLO- 系)

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| GLO-01 | 用語集にない業務用語 | ドメイン層の公開型・公開メソッドの名前に、用語集にない業務上の語が使われる | hybrid | Low |
| GLO-02 | 同義語の混在 | 同じ概念が、同じコンテキスト内で2つ以上の名前で呼ばれる(code\_names と synonyms\_deprecated の併用を含む) | static | Medium |
| GLO-03 | 多義語 | 同じ名前が、同じコンテキスト内で別の概念を指して使われる | llm | Medium |
| GLO-04 | 関係の食い違い | has\_part の関係が、コード上で集約内部の所有になっていない、または refers\_to がオブジェクト参照になっている | hybrid | Medium |
| GLO-05 | 非推奨語の使用 | synonyms\_deprecated の語が新しいコードに出る | static | Low |
| GLO-06 | 用語集の欠陥 | 定義が空、循環した定義、code\_names の重複 | static | Low |

GLO-04 は DDD-AGG-04(ID参照)と同じ箇所を指すことがある。その場合は DDD-AGG-04 を主、GLO-04 を also\_accept として扱い、重複して出さない。用語集がないリポジトリでは GLO 系を走らせず、代わりに `/sumidashi:glossary-draft` でコードから用語集の下書きを作る。

## モデルの共通化

同じ業務概念がバラバラに定義・実装されている箇所と、逆に別の概念を無理に1つにまとめた箇所を、両方向で見る。片方だけ見ると「何でも共通化しろ」と言うレビューになるため。

**共通化を勧める条件**:次の3つをすべて満たすときだけ勧める。形が同じでも意味が違うもの(偶然の重複)は勧めない。

1. 同じ境界づけられたコンテキストの中にある
2. 用語集上で同じ概念を指す(用語集がなければ、LLMが定義文を書き出し、一致するかを判定する)
3. 変更理由が同じ。同じ業務ルールの変更で、両方を直す必要がある

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| MDL-01 | 同一概念の重複定義 | 同じコンテキストで、同じ概念を表す型が2つ以上ある(属性の集合が7割以上重なり、上の3条件を満たす) | hybrid | Medium |
| MDL-02 | 業務計算の重複実装 | 同じ業務計算(税込金額、ポイント付与、手数料など)が2か所以上で別々に実装されている | hybrid | High |
| MDL-03 | 値オブジェクトにすべき組の散在 | 金額と通貨、開始日と終了日など、いつも一緒に扱う値の組がバラの引数で3か所以上に出る | hybrid | Medium |
| MDL-04 | 状態・区分の文字列散在 | 状態や区分が文字列・数値リテラルのまま、3か所以上で比較されている | static | Medium |
| MDL-05 | 誤った共通化 | 別コンテキスト、または別概念を1つの型にまとめた結果、片方の都合だけのフィールドや種別分岐が増えている | llm | Medium |
| MDL-06 | 共有の型の再定義 | 共有カーネルとして定義済みの型があるのに、同じものを再定義している | static | Low |

MDL-02 を High にしているのは、重複した業務計算は片方だけ直されて結果が食い違い、金額の不整合に直結するため。検出は、コードクローン検出(jscpd 等)で候補を出し、LLMが「同じ業務計算か」を判定する。

## ビジネス視点のレビュー

設計が業務の要求とルールを正しく反映しているかを見る。施策の良し悪しは判定しない。判定するのは、書かれた業務要求とコードの整合だけ。根拠のない「ビジネス的にはこうすべき」という意見を出さないため。

**入力**

- **業務ルール台帳** `docs/business-rules.yml`:ルールID、ルールの文、根拠(規約・契約・法令・社内決定)、変更頻度、重要度、実装箇所、テスト
- **サブドメインの分類**:台帳で各領域を core(競争力の源泉)/ supporting / generic に分ける
- **PRに紐づくチケット**:受け入れ条件。PR本文のリンクから取得する

```yaml
- id: BR-012
  rule: 会員ランクがゴールド以上の注文は、送料を無料にする
  basis: 会員規約 第8条
  subdomain: core
  change_frequency: high      # 年に数回、キャンペーンで条件が変わる
  implemented_in: [src/order/domain/shipping-fee.ts]
  tests: [tests/order/shipping-fee.spec.ts]
```

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| BIZ-01 | 台帳と実装の断絶 | 台帳のルールに実装箇所がない、または指す箇所がコードに存在しない | static | High |
| BIZ-02 | 同じルールの実装の食い違い | 1つのルールが複数箇所で実装され、条件や値が食い違う | hybrid | High |
| BIZ-03 | 変わりやすいルールのハードコード | change\_frequency が high のルールの閾値・率・期間が、コードに直書きされている | hybrid | Medium |
| BIZ-04 | 業務ルールのテスト欠落 | 重要度が高いルールに、ルールの条件の境界を確かめるテストがない | static | Medium |
| BIZ-05 | 受け入れ条件との不一致 | チケットの受け入れ条件のうち、コードで満たされていないもの、または逆の動きをするものがある | llm | High |
| BIZ-06 | 金額・数量・日時の扱いの誤り | 金額に浮動小数、台帳と違う丸め、タイムゾーンを持たない日時で締め日を判定、など | hybrid | High |
| BIZ-07 | 台帳にない業務ルール | 業務上の条件分岐がコードにあるが、台帳に対応するルールがない | llm | Low |
| BIZ-08 | 設計の重さと業務上の重要度のずれ | generic な領域に重い設計をしている、または core の領域がトランザクションスクリプトのまま複雑化している | llm | Info |

**重大度への反映**:台帳で core と分類された領域の指摘は、全系統で1段上げる(Highは据え置き)。generic の領域では、DDD戦術系と MDL 系の指摘を1段下げる。業務上の重要度に応じて、どこで設計の手間をかけるかを変えるため。

台帳がないリポジトリでは BIZ-01〜04・07・08 を走らせない。BIZ-05・06 は台帳なしでも動く。台帳の下書きは `/sumidashi:rules-draft` でコードの条件分岐から作れる。

## ロジックの配置とスケール

「このロジックはエンティティか、ドメインサービスか、アプリケーションサービスか」を、決まった手順で判定する。「サービス」という言葉はドメインサービスとアプリケーションサービスの両方に使われ、ここが曖昧なままだと、ロジックがサービスに集まって大きくなるため。

スケールは2つを指す。

- **コードのスケール**:機能・人数が増えても、変更が1か所で済むこと。判断をできるだけ内側(データを持つ型)に置くほど、変更が局所化する
- **実行時のスケール**:負荷が増えても、サーバーを横に増やせば済むこと。サービスに状態を持たせないことと、即時の一貫性が要る範囲を小さく保つことが効く

**配置の判定手順**:Q1から順に確かめ、最初に「はい」になった場所に置く。内側に置けるものを外側に置かないための順番。

&#91;embedded content: ロジック配置の判定手順 · Q1から順に\]

判定の前に、DB・API・時刻・乱数などの外部I/Oを含むロジックは、I/Oと判断を分けてから判断の部分だけをこの手順にかける(CA-HUM-01)。指摘には、どのQで結論が出たかを必ず添える(例:「Q2ではい。送料の判断は Order の状態だけで決まるので Order のメソッドに移す」)。`/sumidashi:plan` での配置提案も同じ手順を使う。

**既存チェックとの対応**:配置の誤りのうち、典型的なものは既存のチェックで拾う。新しいIDは作らず、判定手順の結論を根拠として添える。

| 実際の置き場所 | 手順の結論 | 拾うチェック |
| --- | --- | --- |
| コントローラ・ハンドラ | Q2〜Q6 のどこか | CA-UC-01 |
| アプリケーションサービスやドメインサービス | Q2(単一のエンティティ) | DDD-SRV-01、DDD-ENT-02 |
| アプリケーションサービス | Q3(集約の不変条件) | DDD-AGG-02 |

**新しいチェック**

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| PLC-01 | エンティティが外部を呼ぶ | エンティティ・値オブジェクトが、リポジトリや外部サービスを呼んでいる | static | High |
| PLC-02 | ドメインサービスが手順を調整している | ドメインサービスがリポジトリでの取得・保存、通知、トランザクション制御を行う(Q6の仕事をしている) | hybrid | Medium |
| PLC-03 | アプリケーションサービスに業務判断 | アプリケーションサービスが、ドメインオブジェクトの状態で業務上の分岐・計算をしている(Q2〜Q4の仕事をしている) | llm | Medium |
| SCL-01 | サービスが状態を持つ | アプリケーションサービス・ドメインサービスが、リクエストをまたいで可変な状態(インスタンス変数、モジュール変数のキャッシュ)を持つ | hybrid | High |
| SCL-02 | 即時でなくてよい処理の同期化 | 業務上すぐに反映しなくてよい処理(通知、集計、他集約の更新)が、同じトランザクションに含まれている | llm | Medium |
| SCL-03 | ドメインロジック起因の過剰な読み込み | ループ内のリポジトリ呼び出し(N+1)、または判断に不要な集約全体の読み込み | hybrid | Medium |
| SCL-04 | 読み取りを集約経由で組む | 一覧・集計など読み取り専用の画面を、集約を大量に読んで組み立てている(読み取りモデルを分ける候補) | llm | Low |
| SCL-05 | 更新が集中する集約 | 多くのユースケースが同じ集約インスタンスを更新し、競合の焦点になる構造(グローバルなカウンタ、在庫の単一行など) | llm | Medium |

SCL-02 は「即時でなくてよいか」をコードから決められない。業務ルール台帳に `consistency: immediate | eventual` があればそれに従い、なければ borderline(要確認)に留める。実行時の性能そのもの(応答時間、スループット)は測らない。見るのは、横に増やせなくなる構造だけ。

## 契約・規約・形式手法・OWLの拡張

4領域とも、確定できる部分は既存ツールに任せ、プラグインはツールの結果を設計チェックの言葉に翻訳して集約する。自前で再実装すると精度で既存ツールに勝てず、評価の手間だけが増えるため。

| 領域 | 対象ファイル | 任せる既存ツール | プラグインがやること |
| --- | --- | --- | --- |
| スキーマ・契約 | OpenAPI、JSON Schema、型定義 | oasdiff(破壊的変更の検出)、スキーマ検証器 | 実装との突き合わせ、ドメイン型の露出、用語集との整合 |
| コード規約 | ESLint・Ruff の設定、命名規約 | Prettier・Ruff(書式)、ESLint・Ruff(lint) | 書式は扱わない。層マップと役割に関わる規約だけを見る |
| 形式手法 | TLA+、Alloy の仕様 | TLC、Alloy Analyzer(モデル検査) | 仕様とコードの対応づけ、不変条件の実装漏れ |
| OWL/RDF | .ttl、.owl | ELK・HermiT(推論器)、SHACL検証器 | 推論器の結果の翻訳、モデリング上の落とし穴の判定 |

**スキーマ・契約(SCH-)**

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| SCH-01 | 定義と実装の不一致 | OpenAPI の入出力定義と、ハンドラの引数・戻り値の型が食い違う | static | High |
| SCH-02 | バージョン据え置きの破壊的変更 | 必須項目の追加・削除・型変更があるのに、APIのメジャーバージョンが変わらない | static | High |
| SCH-03 | ドメイン型の露出 | ドメイン層の型がそのままスキーマの元になっている(生成元がドメイン型) | hybrid | Medium |
| SCH-04 | 用語集との食い違い | スキーマの項目名・説明が用語集の用語や非推奨語と合わない | hybrid | Low |
| SCH-05 | 同じ形の重複定義 | 同一構造のスキーマや型が2か所以上で手書きされている | static | Low |

**コード規約(CNV-)**:書式とlintの指摘は一切出さない。出すのは設計に関わる規約だけ。

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| CNV-01 | 層と配置の不一致 | 役割(リポジトリ実装、ユースケース等)と置かれたディレクトリの層が合わない | static | Medium |
| CNV-02 | 役割の命名規約違反 | プロジェクト規約の役割サフィックス(`*Repository`、`*UseCase` 等)と実際の役割が合わない | hybrid | Low |
| CNV-03 | 設計チェックを黙らせる無効化 | `eslint-disable`・`noqa` で、依存方向や循環を検出するルールが無効化されている | static | Medium |

**形式手法(FML-)**:仕様とコードの対応は `specs/mapping.yml`(仕様の変数・アクション ↔ コードの型・メソッド)で人が与える。対応表がない仕様は FML-04 以外を走らせない。

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| FML-01 | 不変条件の実装漏れ | 仕様の不変条件に対応する検証が、対応先の集約・型にない | hybrid | High |
| FML-02 | 仕様にない状態遷移 | コードに、仕様のアクションに対応しない状態遷移がある | llm | Medium |
| FML-03 | 対応表の陳腐化 | mapping.yml が指す型・メソッドがコードに存在しない | static | Medium |
| FML-04 | モデル検査が通っていない | 仕様が変更されたのにモデル検査が未実行、または反例が出ている | static | High |

**OWL/RDF(ONT-)**:オントロジーの落とし穴の分類は、Poveda-Villalón らの OOPS!(OntOlogy Pitfall Scanner)の落とし穴カタログを原典にする。

| ID | チェック内容 | 違反とみなす条件 | 判定方式 | 既定の重大度 |
| --- | --- | --- | --- | --- |
| ONT-01 | 充足不能なクラス | 推論器がクラスを充足不能と判定する | static | High |
| ONT-02 | 循環したクラス階層 | subClassOf が循環し、等価クラス宣言がない | static | Medium |
| ONT-03 | 定義域・値域の欠落 | オブジェクトプロパティに domain / range がない | static | Low |
| ONT-04 | ラベル・定義の欠落 | クラス・プロパティに rdfs:label か skos:definition がない | static | Low |
| ONT-05 | is-a と part-of の混同 | 部分・全体の関係が subClassOf で表されている | llm | Medium |
| ONT-06 | クラスとインスタンスの混同 | 個体であるべきものがクラスとして定義されている、またはその逆 | llm | Medium |

ドメイン用語集(GLO)と OWL を両方持つリポジトリでは、用語集を変換したOWLを ONT 系にかけ、用語集の構造的な欠陥もここで拾う。

## 機能要件

1. **設計相談モード** `/sumidashi:plan <やりたいこと>`
   - 要件を聞き、ルーターが適用思想を選んで、レイヤー・境界・主要な型の案を出す
   - 案は2つまで。採らなかった案の理由も1行で残す
2. **レビューモード** `/sumidashi:review [パス or git差分]`
   - 引数なしなら現在ブランチの main との差分を対象にする
   - ルーターが対象の粒度を判定し、該当スキルだけを並列のサブエージェントで実行する
   - 各サブエージェントの指摘を集約し、重複をまとめ、思想間の衝突をルーターが裁定してから出力する
3. **単一思想モード** `/sumidashi:check <思想名>`:特定の思想だけで見る
4. **解説モード** `/sumidashi:explain <チェックID>`:原則・理由・違反例・修正例を返す。学習用
5. **プロジェクト設定** `.claude/sumidashi.yml`
   - 適用する思想、厳しさ(`lenient` / `standard` / `strict`)、無効化するチェックID、ディレクトリ別の層の対応(例:`src/domain` = ドメイン層)
   - 設定がなければ規模判定から自動で決める。`/sumidashi:setup` を1回実行すると、設定ファイル・用語集・業務ルール台帳の下書きをまとめて作る
6. **自動トリガー**:「設計」「アーキテクチャ」「リファクタ」「レビュー」などの依頼で、明示しなくてもルーターが読み込まれる
7. **hooks(任意)**:PR作成前に重大度Highに当たるチェックだけを簡易実行し、警告を出す。ブロックはしない

## 出力仕様

レビュー結果は「総評 → 指摘一覧 → 採点」の順で、人が読むMarkdownと機械が読むJSONを同時に出す。

指摘1件の必須項目:

| 項目 | 内容 | 例 |
| --- | --- | --- |
| id | チェックID | `DDD-AGG-02` |
| severity | High / Medium / Low / Info | High |
| location | ファイルと行範囲 | `src/order/service.ts:42-67` |
| evidence | 該当コードの要約(引用は10行以内) | 注文の合計金額を集約の外から直接書き換えている |
| principle | 破っている原則を1文で | 不変条件は集約ルートを通してのみ守る |
| suggestion | 修正方針と、可能なら差分案 | `Order.addItem()` に計算を移す |
| verdict / detection | 判定(violation / borderline)と、判定方式(static / hybrid / llm) | borderline は「要確認」欄に出す |
| tradeoff | 直すコストと、直さない場合の影響 | 変更3ファイル。放置すると金額不整合のバグ源になる |

採点は思想ごとに0〜10点。点数だけでなく「何を直せば何点上がるか」を添える。重大度Highが1件でもあれば総評の冒頭に出す。

## 非機能要件

- **コンテキスト効率**:SKILL.md は各200行以内。詳細・言語別の例は `references/` に分け、必要な時だけ読む
- **精度**:誤検知を減らすことを優先する。確信が低い指摘は「要確認」に分け、本体の指摘一覧に混ぜない
- **再現性**:同じ入力に5回レビューをかけて、重大度High/Mediumの指摘集合のJaccard係数の平均が0.8以上
- **速度**:差分500行のレビューが5分以内に終わること
- **拡張性**:思想を1つ足すのは、スキルフォルダ1つの追加とルーターの対応表1行の追記だけで済むこと
- **日本語対応**:出力言語は利用者の言語に合わせる。チェックIDと原典の用語は英語のまま残す
- **安全性**:外部への送信なし。コードの読み取りと差分案の提示のみで、ファイルを書き換えるのは利用者が承認した時だけ

```
│   └── pre-pr-check.json
├── schemas/
│   └── finding.schema.json          # 指摘のJSONスキーマ
└── evals/
    ├── fixtures/                    # 違反を仕込んだサンプルコード
    └── expected/                    # 期待する指摘
```

チェック項目は `checks.yml` に集約し、SKILL.md からは参照するだけにする。チェックの追加・無効化をコード変更なしで回せるようにするため。

静的解析の道具は `tools/static/` に置く。TypeScript は dependency-cruiser(依存ルール)と tree-sitter(AST)、Python は import-linter と tree-sitter を使う。層マップを1つの設定から各ツールの設定に変換するスクリプトもここに置く。

## 評価・受け入れ基準

チェックIDごとに適合率・再現率を測り、合格したチェックだけを既定で有効にして出荷する。詳細は 評価設計。

v1.0 の受け入れ条件:

- 既定の重大度がHighのチェック(8個)すべてで、ホールドアウトの適合率0.85以上・再現率0.85以上
- 有効化されたチェックが27個中20個以上
- 小規模・CRUD中心のサンプル20本で、ddd-tactical の指摘が0件
- 同じ入力5回実行での指摘集合の一致(Jaccard平均)が0.8以上
- 社内パイロット4週間で、指摘の採用率40%以上、「誤り」評価10%以下

## 普及戦略

使われなければ精度を上げても意味がない。一番のリスクは「最初に外して信用を失う」ことと「準備が重くて試されない」ことの2つで、戦略はこの2つを潰すことに寄せる。

**KBF(利用者が導入を決める理由)**:重要な順。

| # | KBF | 利用者の言葉 | 応える仕組み |
| --- | --- | --- | --- |
| 1 | 指摘が当たる | 「外れが続いたら見なくなる」 | チェック単位の出荷ゲート、borderline の分離 |
| 2 | 導入が軽い | 「設定に半日かかるなら試さない」 | 設定なしで動く既定値、層マップの自動推定 |
| 3 | 今のフローを邪魔しない | 「PRの待ち時間が増えるのは困る」 | PRコメントへの出力、差分500行を5分以内 |
| 4 | 直し方まで分かる | 「指摘だけなら自分でも気づける」 | 差分案付きの suggestion、判定経路(Q番号) |
| 5 | レビューで揉めない | 「AIが言ってるだけ、と言われたくない」 | 原則・原典・ADR番号を必ず添える |
| 6 | 空気を読む | 「小さいコードにDDDを押し付けないで」 | 規模判定、ADRによる例外、サブドメイン分類 |

**KSF(こちらが外せないこと)**

1. **初回体験で誤検知を出さない**:導入直後の2週間は、適合率0.9以上のチェックだけを有効にし、strict は使えないようにする。「数は少ないが全部当たる」から始め、信頼ができてから広げる
2. **コールドスタートを潰す**:ADR・用語集・業務ルール台帳を手で書かせない。`/sumidashi:setup` を1回打つと、層マップ・用語集・業務ルール台帳の下書きをコードから作り、人は確認して直すだけにする
3. **精度を公開する**:チェックごとの適合率・再現率と、社内での「役立つ」率をダッシュボードで常に見せる
4. **既存の場所に出す**:GitHubのPRコメントとCIを主な出口にし、コマンドを打たなくても結果が届くようにする
5. **1チームで深く成功させる**:全社に薄く配らず、最初の1チームで数字と事例を作ってから横に広げる
6. **使うほど当たるようにする**:「誤り」と付いた指摘を正解データに戻し、翌月の評価に入れる

**KPI**

| 種類 | 指標 | 定義 | 目標(パイロット4週間) |
| --- | --- | --- | --- |
| 先行 | 導入完了率 | `/sumidashi:setup` を実行したリポジトリのうち、1週間以内に最初のレビューまで進んだ割合 | 80%以上 |
| 先行 | 初回体験の誤り率 | 導入から2週間の指摘のうち「誤り」評価の割合 | 5%以下 |
| 利用 | 週次の継続利用 | 4週目にもレビューが走っているリポジトリの割合 | 70%以上 |
| 価値 | 採用率 | 指摘のうち、次のコミットまでに該当箇所が直された割合 | 40%以上 |
| 価値 | 人のレビューの手戻り | 人のレビューで設計に関する差し戻しが起きたPRの割合(導入前と比べる) | 導入前から30%減 |
| 価値 | 設計起因の不具合 | 障害・バグ報告のうち、原因が v1 チェックの対象だったものの件数 | 四半期で前年同期比減(長期指標) |

**広げる順番**

1. **パイロット(1チーム・4週間)**:設計への関心が高く、ADRが既にあるチームを選ぶ。週1回、指摘の当たり外れを一緒に振り返る
2. **同じ事業部内の3〜5チーム**:パイロットの数字と事例を持って広げる。`/sumidashi:setup` の下書き精度をここで詰める
3. **全社(社内marketplaceで配布)**:導入手順を5分で終わる形にし、社内の勉強会と新卒向けの研修教材(`/sumidashi:explain` を使った演習)をセットで出す
4. **OSS公開(任意)**:社外の実例で正解データを増やせるなら検討する
